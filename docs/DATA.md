# 📦 DATA.md — происхождение данных и правило их использования

Документ фиксирует, какие данные проект использует, откуда они взяты и чего в проекте быть не должно.

## 1. Правило: данные из `old/` не используются

В корне рабочей папки есть каталог `old/` — это **старый прототип** (Go-сервисы и HTML-UI). В нём лежали
31 фотография этикеток (`old/services/*/test_obj/`), которые ранее копировались в проект и использовались
для оценки.

**Решение: эти данные не используются нигде** — ни для обучения, ни для оценки, ни для демонстрации.
Они исключены из проекта полностью, включая производные артефакты (отчёты, логи, подтверждённые метки).
Причина: данные не входят в официальный комплект конкурса, происхождение и права на них не подтверждены,
а метрики на них несопоставимы с оценкой организатора.

Правило закреплено в:
- `AGENTS.md` → раздел Constraints;
- `.grace/context/constraints.xml` → правило D-3;
- `.grace/context/requirements.xml` → аномалия AN-3;
- `.grace/verification/VD-M-DATA.xml` → запись **V-M-DATA** с машинными проверками.

## 2. Что используется

| Источник | Путь | Назначение |
|---|---|---|
| Каталог «Своё Вино» (CSV) | `материалы для конкурса/Датасет/strapi_output0709.csv` | метаданные 2103 позиций |
| Sitemap вин | `…/uploads/wines_sitemap_*.xml` | авторитетный маппинг slug → эталонное фото (2037 записей) |
| Эталонные фото | `…/uploads/*.webp` | построение векторного индекса и признаков геоверификации |
| Контрольные фото организатора | `data/samples/eval_queries/` (2 файла) | демонстрация и измерение latency на официальных данных |
| Синтетический «полевой» набор | генерируется `scripts/eval/augment.py` | proxy-оценка качества (seed фиксирован) |

Материалы конкурса в git не попадают: они лежат вне репозитория, а `data/` и `models/` внесены в
`.gitignore`. В репозиторий попадает только **код**, который эти материалы читает.

## 3. Как воспроизвести данные

```bash
make etl      # CSV + sitemap → data/catalog/{catalog.jsonl, slug_to_image.json, stats.json}
make index    # эталонные фото → data/index/{vectors.npy, slugs.json, meta.json, features.npz, head.pt}
```

Каталог: 2103 уникальных slug, 2037 с эталонным фото, 66 без фото (см. `docs/LIMITATIONS.md`).

## 4. Почему нет публичного полевого набора

Организаторы заявляли ~100 полевых фотографий; фактически в официальном комплекте переданы
**2 контрольных фото** для проверки работы скрипта оценки. Полноценный полевой набор используется
только на приватном прогоне у кейсодержателя.

Следствие: F1@1/@5 измеряется на **синтетическом proxy-наборе** (`scripts/eval/baseline_report.py`),
а официальные фото дают демонстрацию и latency. Это ограничение честно зафиксировано в
`docs/LIMITATIONS.md` и в отчётах (`reports/baseline.json` → поле `note`).

## 5. Что делать, если появятся официальные полевые фото

1. Положить их в `data/samples/<набор>/` (папка вне git).
2. Завести `ground_truth.tsv` формата `query_id<TAB>slug`.
3. Прогнать `scripts/eval/evaluate.py --images data/samples/<набор> --ground-truth <tsv>`.
4. Перекалибровать пороги: `scripts/eval/calibrate.py` (пороги зависят от домена данных).
5. Обновить `docs/LIMITATIONS.md` и запись V-M-EVAL фактическими цифрами.
